# 方案送审与意见回收

这是调用方的流程。审核方收到自足请求后，直接讨论方案，不必再读整套协作流程。用户仍可说 `ctx-review to claude`、自然语言送审或“审核好了”，不新增用户命令。

## 用户确认

> 你们的讨论结果一定要经过我确认后再改文件，

先向用户展示讨论结论、拟改范围及影响，得到明确确认后再落实修改。双方一致、回执完成都不替代用户确认；已经确认的同一结论和范围不重复询问。

## 准备

1. 确认本次是送审、审核还是回收。复用已明确的目标、读者、场景和材料，不重复追问。未指定审核方时沿用明确上下文，没有依据才问。协作记录与上下文检查另用 ctx-checkup。
2. 按被审方案所属项目定位原案或任务，沿用其审核目录；无约定时用 `_ops/REVIEWS/<案号或任务ID>-R<轮次>/`。不因技能安装目录或 Git 父根改变归属，不抢占其他持笔，按[共用方法](../docs/METHOD.md)登记 E/I。
3. 用[请求模板](../templates/REVIEW-REQUEST.md)写清需要讨论的问题，附必要原文。区分全文、摘录和未提供部分，避免只给作者摘要；框架讨论围绕思路、逻辑、衔接与覆盖，关键细节是否深查由目标和实际影响决定。后续轮次只列未决 ID、变更点及相关前轮意见，不重复全稿挑问题。
4. 调用方保存核心快照、输入清单和版本哈希，排他创建轮次目录；既有请求和完整回执不覆盖。文件可读性、版本、身份和运行日志由调用方核验一次，不作为审核方必须重复完成的清单。引用默认是背景，不因有链接就要求逐网站核查。

## 发起与收敛

用户明确要求送 Claude 审核时，默认按[CLI 调用约定](review-cli.md)发起并回收；调用方式、默认模型和进度监测由调用方处理。审核方只需当前请求、必要原文和前轮未决。若用户明确选人工链路，则给可复制提示，待其告知或出现回执后回收；不可用时先报具体原因，不擅自改登录、权限或旧审核入口。

同一审核目标通常 1–2 轮、最多 3 轮内容往返，全任务最多 1 次技术重试。调用方在原案 E 记录已用次数；修订、补材料、换会话或轮次编号不重置。只为影响重要判断、且有望增加证据或改善方案的问题追加轮次；已有充分结论即可提前停，到上限交推荐方案与剩余分歧。用户明确要求重跑或改预算时，保留原记录及授权依据。

进程有有效进展就继续等待，时间用于监测提醒，不默认设固定终止线。长期无进展时检查输出、错误和执行状态并报告；不能仅凭 PID 存活就认定正常，也不能因一次等待工具返回超时就重启。需要用户补材料、登录或审批时明确报告阻塞。

## 审核方

直接按请求独立判断整体思路，提出有实质影响的异议、反例或替代方案，说明理由与取舍。可以认可合理部分，不凑问题或强制输出分类表。不默认逐句校对、逐链接核验或重复已有验证；只有会改变结论的具体事实疑点才定点核对，无法确认的事实如实标出。

以用户问题判断内容覆盖，不以章节和概念数量凑齐结构；在已给材料范围内判断，不能把没看到当作不存在。重要意见要有实际影响，偏好不自动成为必改项。用户认可的原句和结构仍可被质疑，但未经确认不落实改写。

CLI 审核只输出正文，由调用方原样保存；人工文件审核只写指定独立回执。不认领原案、不修改被审材料或案板、不自行调用另一模型。身份与哈希由调用方记录，审核方不重复探查。缺少决定性材料时直接说具体缺口。

## 回收与交付

调用方核对请求对应关系、输入版本和交付是否完整，原样保留审核意见并另外写[处置](../templates/REVIEW-DISPOSITION.md)。CLI 的退出成功不等于方案通过；旧包的 `REVIEW_COMPLETE` 只表示回执完成。仅缺形式标记、但内容完整且请求匹配时，可核读后记录“协议偏差接收”，不伪造原文或为补标记再调用模型；无法确认完整则保留部分结果并说明。

持笔按原文、证据和用户目标独立取舍，可以接受对方更好的整体方案。先给用户整体结论、推荐方案、关键共识/分歧与必要改动，按需附精简处置记录。重要异议未被采纳时保留原句和理由，不冒称共识；真正需要用户决定的问题转达用户，已有明确答案的事实问题由持笔引证据回答。

回收完成、建议已落实、真实验证是不同状态。模型共识和假设例子不代表实际效果已验证；确认之前不按讨论结果改文件。执行者交独立结果，原持笔回填 E/I；未决和用户决定分别进入 D/C。
