# 方法说明文档写作

把一项工作的方法写成读者可以理解、判断和运用的说明。围绕读者的实际问题组织全文，让每一节推进问题；不按讨论轮次堆资料。

## 判断用途与输入

适用于工作方法或流程指南、判断或评估方法、面向实践的概念说明，也适用于解释“怎样编制需求或变更规格”的方法文档。直接编写规格、接口和验收条款时，保留其精确约束及必要结构；README、任务板、案卷、历史快照、短邮件和纯数据报告不因采用 Markdown 就套用本流程。简短职场改写与本技能的任务不同。

复用上下文中的主题、读者、希望帮助读者完成的工作或判断、材料与篇幅要求。只有缺项确实妨碍写作时才追问，不要求用户重复填表。用户明确调用了本技能但任务属于上述其他文类时，说明适用边界，按其实际文类和要求处理；用途不清才澄清。

## 先区分讨论与写入

遵守用户的修改边界，保留这条原规则：

> 当我对文档有异议时，你先回复异议，然后经过我同意后，再写入文档，不要直接修改文档

用户表达异议、质疑某个观点或指出写法有问题时，先回应问题，给出判断及拟调整方向，取得明确同意后再写入文档。讨论中的候选内容仍标为建议或待验证。明确的创建或修改请求按已有授权执行，无需额外制造确认环节；例如“把这段改为以下文字”可以直接修改。只要求讨论时，在对话中回应，不擅自创建或保存正文。

## 选择阅读主线

先用一句话说明全文如何帮助读者解决问题，再按用途展开。下表是组织依据，不是三个必须逐一执行的阶段。

| 用途 | 主线及必要内容 |
|---|---|
| 工作方法或流程指南 | 按工作怎样推进组织：每步回答什么、开展什么工作、形成什么必要输出，以及它怎样供下一步使用。按实际需要保留责任、约束和继续、返回或停止条件。 |
| 判断或评估方法 | 按取得依据与作出取舍的过程组织：判断对象、标准、替代办法、证据、权衡和适用边界；证据不足时保留未知，说明怎样补充或暂缓判断。 |
| 面向实践的概念说明 | 按概念解决的理解问题及相互关系组织：解释、贯穿例子、用途和边界；不强行为每节创造步骤或输出物。 |

可裁剪骨架：**背景 → 目标 → 阅读主线 → 按主线展开的方法或关系 → 使用边界 → 参考依据**。按读者需要合并或省略，不固定章节数、步骤数或独立交付文件。

背景简要解释为什么开展这项工作；目标说明工作需要达成的结果，不写成“本文旨在编写……”或内部协作任务。两者避免重复展开。

## 展开正文

- 在需要概念的位置解释到足以支持当前理解和行动。庞大的方法目录、资料考据和过程记录放在适当的参考或工作记录中，保留正文主线。
- 用少量可贯穿的例子说明关系，说明性假设与真实事实分开。工作步骤交代必要输出和下一步用途，图表与说明可以合并维护；不为形式齐全增加独立文档。
- 用连贯段落发展判断。表格用于比较、对应和简洁检查，不把全文写成标签清单，也不省略必要责任、约束或判断依据。
- **核心判断加粗。用户明确赞许或指定保留的句子逐字保留并加粗，不用新的概括替换。** 认可整篇风格不表示整篇加粗；只保留与当前文档相关的认可句子，不把范例原句硬套进其他主题。
- 成熟方法保留官方来源链接，解释具体支持的内容及边界。新增或实质更新来源性论断时核对来源；无法核实时明确标注，不能虚构链接或查阅日期。区分来源事实、作者综合、候选建议与待验证内容，不因写进正文就把建议变成结论。
- 正文应能脱离原项目独立阅读：解释必要术语，去掉对当前聊天的依赖。案号、中间产物、维护任务和讨论来历留在过程记录；不要把这些内容写进通用方法正文。

## 范例怎么用

需要对齐篇章节奏、段落展开或输出说明时，读取 [认可写法范例](../docs/METHOD-WRITING-EXAMPLE.md)。这是固定的写法参考；其中的五段业务步骤、七项观察方面和业务主题不是通用模板，方法主张也不因被收录就已经验证。

从范例借鉴主线、衔接、概念解释、少量例子、核心句加粗和来源范围的处理。根据当前文档用途重新组织内容，保留用户的既定格式和精确约束。

## 交付前检查

从读者视角通读：能否理解为什么开展工作、从哪里入手、怎样继续或据什么判断？检查是否按用途组织，是否存在无依据的结论、丢失的约束、被改写的认可句子、无用的输出物和依赖聊天的文字。

按用户指定的格式与位置交付；文件写入当前任务的目标项目，技能目录仅存技能资源。已有案的进展由持笔更新，不因普通写作单独开案。回复简要说明产出、实际核对及仍需验证的内容；结构检查不能证明方法有效或写作效果已经全面验证。
