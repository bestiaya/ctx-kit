# 共用协作方法

状态按工作组织，过程按会话保留。案号与任务 ID 稳定；换会话不另建相同工作的账。

## 1. 项目与案库

先确定用户本次工作所属的项目或子项目。用户指定路径、项目指令、已有任务板优先；Git 根只能帮助定位，不能把 monorepo 中每个子项目自动归入顶层案库。

只在已确定的项目范围内找：先用明确指定的案库，再用已有 `_ops/CASES/`，否则已有 `cases/`；均无时默认创建项目内 `cases/`。多个库归属不明确时，只问一次目标库。首次写入前报告绝对路径；已明确授权的项目内建案不再增加确认关卡。安装位置不是目标项目位置。

任务板使用案库内 `TASKBOARD.md`，已有 `_ops/TASKBOARD.md` 等位置可沿用。任务书、交付件和审核数据沿用已有目录；没有约定时用项目内 `_ops/TASKS/`、`_ops/DELIVERIES/`、`_ops/CONTEXT-AUDIT/`，按需建。方案内容送审使用 [ctx-review 流程](../workflows/review.md)，默认轮次材料在所属项目 `_ops/REVIEWS/`；协作与上下文检查仍使用 `_ops/CONTEXT-AUDIT/`。

## 2. 板、案、件、档

| 载体 | 内容 | 维护方式 |
|---|---|---|
| 任务板 | 总目标、目标节点、案/任务索引、全局待决 | 不复制案的详细状态；查询时从案汇总。已有自动投影由原生成器维护 |
| 案头（案文件） | 目标与验收、当前位置与下一步、继任阅读表、工作方式与有效约束、未结的未决、在跑任务、缺口、待处理来件 | 持笔维护，是本案当前推进状态的事实源；产品方案、规则与决策已有事实源时只留短结论与指针，不另存一份正文 |
| 案的记录文件 | 决策记录（C 全表）、实验记录（E 已完成行与 G）、过程记录（F、I 已处理行、交接回执与接手读量） | 持笔随事项追加；继任按下一步定点读，不整读 |
| 任务书 | 一次执行的目标、输入、约束、判据、输出位置 | 派发前固定；输入里的读物按继任阅读表的写法标读取时机（开工前 / 做到某事时），给新案开工用的任务书也照此写；改变判据应留变更说明，不事后改成“通过” |
| 交付件 | 结论、实际验证、数据路径、未完成项 | 完成的交付留版本；更正产生新版本并说明替代关系 |
| 会话档案 | 历史讨论、工具输出 | 平台管理，按需定点取证，不整份读入新会话 |

过程记录与对外交付分开。对外材料只带用户需要且允许发布的结论，不夹带内部案文、私人路径或讨论过程。

新建记录用 [任务板](../templates/TASKBOARD.md)、[案头](../templates/CASE.md)、[案的记录](../templates/CASE-RECORDS.md)、[任务书](../templates/TASK.md)、[交付](../templates/DELIVERY.md) 模板；已有记录按语义对应，不为改格式重写历史。

## 3. 案的字段

头部记录项目范围、案 ID、任期（`stint`）、案状态、交接状态、持笔身份、最近更新时间（带时区）。身份用 `平台 + 会话完整 ID + 可读名称`；名称可改，ID 不随改名变化。拿不到 ID 就写“ID 未取得”，用本次独有的临时标识，身份有歧义时不能覆盖别人。

| 节 | 存什么 | 所在文件 | 怎么更新 |
|---|---|---|---|
| A 目标 | 用户目标、上级目标、已有验收条件 | 案头 | 不编造指标、期限或承诺；未确定的写入 D |
| B 当前方案 | 当前位置（自上次交接以来变了什么）、下一步、继任阅读表、工作方式与边界、仍约束当前工作的决策一句话列表（含否决路线，带编号） | 案头 | 随变化更新；方案全貌在事实源文件的只留指针，旧版在记录文件留痕 |
| C 决策 | 结论、理由、依据、谁决定；含否决路线 | 决策记录 | 追加；修正时新行标明替代哪个决策；仍约束当前工作的在 B 留一句话 |
| D 未决 | 待解决事项、建议、等待谁 | 案头 | 解决后删行，去向写入决策记录或实验记录，不静默丢弃 |
| E 任务/实验 | 任务 ID、载体、状态、任务书、交付、判定及对方案的影响 | 排队、在跑、阻塞、待验收行在案头；完成、取消、已转交行在实验记录 | 持笔回填；验收后移入实验记录，状态变动在过程记录留痕 |
| F 编年 | 关键事件、交接、变更原因、接手读量 | 过程记录 | 追加；案头只留最近一次交接与记录文件指针 |
| G 证据与档案 | 文件、会话 ID、已核验的位置 | 实验记录 | 不靠最近修改时间猜归属；未知写未知；当前要读的事实源列在 B 继任阅读表 |
| H 缺口 | 未完成、未验证、无法恢复或尚未保存的内容 | 案头 | 重列当前缺口；已保存不等于已解决，未验证仍留；已处置行移入过程记录 |
| I 收件位 | 来件 ID、来源、事项、状态、处理结果/证据 | 待处理、处理中、阻塞行在案头；已完成、不采纳行在过程记录 | 接收不等于完成；先比 ID 再开原件；每件可追踪至结果 |

H 必须读，不能因排在文末就忽略缺口。长材料留外部证据，案里保留当前结论和链接。

**案头规模与记录文件。** 案头以 Unicode 字符计（`python3 -c 'import sys;print(len(sys.stdin.read()))' < 案头`），目标 10,000 字符以内，15,000 为整理线；超线先把已结内容移入记录文件，不删未解决事项，移后仍超线在交接回执写明剩余字符数与原因。记录文件与案头同目录、同名加后缀：`<案文件名>_决策.md`、`<案文件名>_实验.md`、`<案文件名>_过程.md`，按 [案的记录模板](../templates/CASE-RECORDS.md) 建，首次需要时建。决策当场追加到决策记录；任务验收后行由案头 E 移入实验记录；来件处理完成后行由案头 I 移入过程记录；编年只写过程记录。旧的单文件案照常可读，接手不强制拆分；超线时由持笔拆分并在过程记录留痕。字符预算不解释为 token、费用或质量阈值；接手阅读的预算见 [接手流程](../workflows/takeover.md)。

### 会话命名

Claude 与 Codex 共用这一套规则。依据是 2026-10-07 核对的本机已安装 Claude `ctx-kickoff` §2/§3 和 `ctx-takeover` §3；此次取代移植时旧快照中的项目会话计数。两端只适配标题和身份工具，不分别定义取号算法。编号后的显示分隔符按 2026-10-09 用户选择改为全角竖线，见下文。

**案内会话名：`C<NN>-<SS>｜<案短名>-<本任期工作>`**，例如 `C07-03｜计费-异步还是流式的决策`。案号 `C-07` 去掉连字符得到 `C07`；`SS` 唯一取自案头的 `任期` / `stint`。数字至少两位，超过 99 不截断。案号和任务 ID 各自稳定，任期表达同一案的接替次数。

| 场景 | 编号来源与操作 |
|---|---|
| 新建案并持笔 | 案头写 `任期：01`，使用 `C07-01` |
| 新会话正式接手已有案 | 通过持笔与并发检查后，将案头已有任期加 1，并与新持笔一起写回 |
| 接手的旧案没有任期字段 | 本次写 `任期：01`，说明“任期从此处起算，早先历史见编年”；不数旧标题 |
| 当前持笔重复开工、重复接手或改工作描述 | 复用本任期，不递增；未被释放的其他持笔不能因取号而被替换 |
| 无案的散活 | `C00-<nn>｜<工作内容>`；`nn` 是任务板独立任务（散活）表的登记行号，表头不计 |
| 派生执行 | `<派发者编号>.<子号>｜<案短名>-<工作内容>-exec`，如 `C07-03.1｜计费-压测-exec`；散活为 `C00-02.1｜压测-exec`，没有案短名 |

- **显示分隔符**：编号与标题内容之间使用全角竖线 `｜`（U+FF5C），两侧不留空格，如 `C07-03｜计费-方案验证`、`C07-03.1｜计费-压测-exec`、`C00-02｜修复脚本`。编号内部仍用半角 `-`，退役前缀仍为 `✕ `；不要换成 Markdown 表格分栏符 `|`。旧空格格式仍可识别，只有用户要求或正常设置新标题时采用新显示，不批量改历史名、不递增任期。
- **认领与重试**：幂等只适用于案头仍由当前身份持笔的同一任期；已释放后获准再次认领，即使会话 ID 相同也按正式接手递增。先保存任期与持笔身份，再尝试标题工具；标题或板同步重试不再加号。当前持笔的旧案缺任期时保留旧名、报告字段缺失，留待正式接手初始化；已有字段无效或中英文两字段冲突时先核实案记录，不猜数。
- **禁止为取号调用会话列表或扫描历史会话找最大号。** 案内读案头，散活读板，子号读派发者的已派记录。列表仍可用于核实身份、状态或地址；返回条数不会改变编号规则。
- **案短名**在开案时固定于任务板名称列，如 `计费策略〔短名：计费〕`；中文二至四字、英文一个词。后续从板读取，不另造。接手旧板缺短名时，由持笔补一个并告知用户；用户可更正。
- **子号仅由派发者分配**：在自己的已派记录中取下一个子号，先写任务书和 E/散活载体，再启动执行。已写入的预留号也占号；同一任务的派发重试沿用派定名，失败或取消留占号记录，不回收给另一任务。执行者沿用已派名；未实际派出不报告已开始，也不因关联某案擅自取得该持笔的子号。旧格式派发者已有编号及已派名继续沿用；无可靠编号就报告缺口，不从会话列表拼造父号。
- **用户指定名优先，运行中的旧名保留。** kickoff 后的任务描述用来生成工作段，不等于要求整个标题原样使用；只有明确要求某个完整标题或保留已有手工标题，才使用指定名例外。不批量重命名历史或仍在运行的旧格式会话。用户明确要求按规则重新命名时，重新核对工作归属和编号来源，不能拿助手刚设错的标题当作必须保留的旧名。新任期采用新格式；同一会话主要工作变化时可改工作描述，保持编号。普通会话默认不加角色后缀，只有实际派出的执行会话加 `-exec`。
- **项目短前缀默认省略**，仅出现真实跨项目重名时加，例如 `ck-C07-03｜计费-决策`；用户指定前缀仍优先。
- **三处同步**：标题成功设置后，持笔将同名写入案头和任务板该案行的持笔镜像；板上持笔仅为投影，以案头为准。旧板缺镜像列时由持笔在维护本案时补齐，其余行不擅填。执行载体由持笔依据实际返回的 ID/标题回填 E 或散活行，执行者保留自己的交付，不并发覆盖案。
- **同步写入边界**：更新板只改本案行或已授权的散活行，按未转义的 `|` 分列，保留单元格内的 `\|`。名称变化不改变完整 ID。UI 成功而案头、板或载体写入失败时逐处记录已完成/待同步，以保存的本任期重试；不把部分同步报成全部完成，也不重写编年中的旧名。
- **身份与改名分别记结果**：标题工具不可用或失败时，报告 UI 名称未同步，持笔/载体使用已核实的原名，或明确写“名称未知/标题工具不可用”；不能把拟定名写成成功设置的名字。已获准接手仍可完成案内任期和身份记录，不因缺标题工具改用全项目计数。若案头写入失败，报告部分完成，重读后处理，不能只凭 UI 成功宣称已认领。
- 仅要求改名时不为凑编号开案。能从既有案、散活行或已派记录定位编号就复用；没有这些依据时保留/采用用户指定名并说明缺口。合并到他人案只进入收件位，不新开任期或自认派生关系。
- 任务板散活行首次登记时记录行号，后续保留已有号，不因表格整理重编号或复用已发出的号。新任务追加登记；取消/归档任务保留占号行及档案指针。旧板缺行号列时，已有登记号按任务书/载体记录补齐，没有登记依据的行以当前登记位置固定并核对板内占号；冲突报告缺口，不改运行中的旧名。交出会话的退役标记按[交接后的会话退役标记](#交接后的会话退役标记)执行；标记不代替释放持笔，释放时保留本任期供继任读取。

## 4. 持笔与并发

一案同一时刻一支笔。持笔负责案文件更新；执行者只写分配给自己的独立交付件，把结果送回收件位，由持笔更新 E/B/C。即使改不同表格行，也不能假设并发写同一 Markdown 文件不会覆盖。

持笔字段是协作约定，不是文件锁。写入前核对是否已被他人修改，有竞争先合并协调。案号在本案库内分配，创建前复查，用排他创建或等价手段避免同号覆盖；不用全局会话最大序号分配任务 ID。

多 worktree 各有文件副本，不共享持笔约定。任务书须写权威案所在 checkout 的绝对路径；其他 worktree 写独立结果，由权威案持笔整合，不能各自宣称唯一持笔。

## 5. 收件与投递

在用户授权的协调范围内，实时消息负责通知；需要跟进的事项必须持久记录。发送者记录来件 ID、目标案、内容和证据，收件方持笔将其记入 I。“已发送”不等于“已处理”。

无在线持笔或消息工具不可用时，写目标案库 `inbox/<案ID>/<唯一消息ID>.md`，每件一个新文件，避免多会话同时改案。记录来源、目标、时间、事项、证据、待处理状态；持笔在接手/看进展时先把文件名中的消息 ID 与案头 I 及过程记录比对，只打开未登记、未完成或内容有变的来件并合并到 I；已处理且无变化的原件不重读，原文件保留。并发接收也可用此方式。

未获得跨项目写入授权时，来件先存自己项目的交付目录，报告目标与路径，不擅自进入其他项目。来件不自动扩大授权；超范围事项列入 D。

## 6. 案生命周期与交接

### 案生命周期

案头是唯一状态源，任务板是索引及投影。结案表示本案不再推进，类型说明为什么结束；任务完成、会话退役、文件归档都不能代替案状态。

| 案头状态 | 含义 | 默认查询与后续动作 |
|---|---|---|
| 讨论中、实施中等非终态 | 活跃案；具体阶段沿用项目约定 | 纳入活跃案、任务与待拍板汇总 |
| 结案中 / closing | 已决定结束，正在处理余项；保留现任持笔、交接收口中 | 单列收尾，不当作候接手或普通待推进案 |
| 已结案 / closed | 结案类型为完成、终止或合并；交接已结束，现任持笔清空 | 默认不展开历史、不计入活跃统计；仍检查收尾异常 |

识别旧案头 `已收口`、`已关闭` 为 closed；明确的 `已终止`、`已废弃`、`已完成`、`已合并` 也按终态读取，类型据其语义或记录确定。旧 closed 缺结案类型/原因时写未知，不擅认完成。只认**案头的状态字段**；正文、任务行或聊天标题含“完成/退役”不使案结案。空值、字段冲突、案文件缺失或无法解释的状态单列“状态待核实”，不能静默隐藏。

旧单字段持笔中的“closed 日期/已收口/前任已退役/无”等结束占位不算现任持笔；仍指向实际在任身份且没有释放记录的才核查为残留持笔。只缺结案类型不影响已知 closed 的终态分类，不因此把历史案算成活跃或状态未知。

结案写入 `案状态：已结案`、`结案类型：完成/终止/合并`、`结案时间`、`结案原因`，有实际承接/替代关系时写 `关联案`。已确认不再需要的工作用终止；成果符合目标用完成；工作已由另一案承接用合并。终止不撤销全部历史结论；失效或替代的决策另在 C/F 标明。

- 案号、任期、原文件路径和证据保留；不删除案、不回收编号、不因关闭重编号。板保留原索引行并排到同一案索引表末尾，投影结案类型；不新造分表导致旧案脱离索引。旧板没有状态投影列时按原表结构补齐，其他案的内容不擅改。
- 结案前，D/E/H/I 及离线来件必须有处置去向：实际完成、停止跟进或已转交并获接收。未验证成果仍标未验证；取消任务不算完成；原始来件和历史保留。处置按事项 ID 记入 H 的结案处置表，转交带目标和接收证据，不能只写一句“所有待办作废”。
- 实际仍在跑的任务、未接收的转交、未处置来件阻止宣告结案完成，保持结案中并报告剩余动作。已结案后到达的新来件、发现的在跑执行、残留持笔或未处置事项，作为**收尾异常**报告；不自动重开，也不因过滤历史而漏掉。
- 转交的接收证据要与目标案的任务/来件记录或可读回执对应。只有一个 ACK 名称或“已转交”字样，而目标缺对应记录、回执不可读或双方矛盾时，报告“转交证据待核实”；不能认定已确认承接。历史案保持终态，同时报告证据异常。
- 普通交接只变交接状态，案仍活跃；结案后不设候接手、不提示下一会话接手。结案不自动归档聊天、终止进程或退出当前聊天。
- 用户明确恢复意图后才重开原案。保留上次结案记录于 F，恢复为讨论中/候接手，当前结案字段清空，随后按正式接手认领并递增任期一次；已经恢复且仍为当前持笔时重试不递增。不自动重启旧任务、复活已拒绝来件或撤销已生效的转交。

实际结案、批量处理与恢复步骤见 [案的结案与恢复](../workflows/case-lifecycle.md)。候选整理是只读工作；仅因案号小、长期不更新或同项目已有新案，不能自动终止。

### 交接状态

案的业务状态与交接状态分开：交接完成不代表工作完成，平台进程“空闲”不代表持笔已释放。

1. 工作中：`交接: 持笔中`，持笔存在。
2. 整理交接：先写 `交接: 收口中`，保留持笔；保存成果、未决、来件、缺口和下一步；已结内容移入记录文件，写继任阅读表并估预计接手总量，案头计字符。
3. 可接手：材料核验、案头在整理线内或回执写明后，记前任身份，清当前持笔，写 `交接: 候接手`。
4. 继任接手：读案头，检查 H、I 及未登记来件，记录文件按下一步定点读，复查头部没有变化，再写新持笔及 `交接: 持笔中`。

候接手时执行任务可以继续跑，E 必须列明载体、输出位置及回收动作。收口中或仍由别人持笔的案，不凭一天未更新、标题或空闲状态强行接管；先确认前任释放、用户明确转交或可靠证据证明执行已终止，并记录依据。

交接不等于自动归档聊天、停进程或发布代码。提交、推送、创建新聊天和跨聊天发消息遵循已有用户授权与平台边界；既有授权不重复询问。

### 交接后的会话退役标记

**交接材料保存、核验通过并释放持笔后，必须给交出的旧会话原标题加 `✕ ` 前缀，不再等待额外的用户标记指令。** 独立执行任务和无案散活须先完成各自的材料交接；不能代关联案释放持笔。单纯结束案未交出会话时，仍按结案流程处理。

- 释放前在交接记录中保存交出会话的平台、完整 ID、原标题及本任期。材料未完成、仍收口中或释放写入失败时，不提前标记；不能把标题变化当作交接成功。
- 只处理本次交出的旧会话。已有 `✕ ` 时保持不变；否则只加一次前缀，保留编号、任期和原标题主体，不改继任标题、不批量补标历史聊天。
- 标记结果单独记入本次交接回执，区分“文件交接及释放完成”与“UI 标记完成”。改名能力不可用、身份/原标题无法可靠取得、工具失败或结果无法确认时，报告标记未完成及原因，不伪造成功，也不改内部数据库或绕过权限。
- 重试标记须核对本次交接记录及已完成的释放证据，只重试旧会话的 UI 操作。不得重新认领、再清一次持笔或覆盖继任的案头/任务板；释放后的记录补充写独立回执，不冒充现任持笔回填。
- 退役前缀仅作识别，不删除、归档或关闭聊天，不改变案的业务状态，不自动创建继任或提交推送。原会话仍可响应后来请求；需要重新持笔时走正式接手，不因符号拒绝工作。

## 7. 执行与验证

派活按方向不确定性、输入边界和交付方式选载体。需要人持续参与的设计适合独立聊天；范围闭合的子任务可在平台允许且已获授权时委派。中途沟通能力现场确认，不写成跨平台限制。

独立验证任务只给原始输入、目标和事先约定的判据，不灌入预期结论；共享了讨论观点的检查如实标为非独立。代码测试、静态检查、实际交互和真实复杂任务验收分开记录。

经济与质量策略见平台 EVIDENCE；没有实测结论时，不自动按 500k、一小时或 50% 结束会话。
