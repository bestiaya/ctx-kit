# 业务需求起点与信息系统基础

更新：2026-10-09。工作稿；下文提出的分析组织方式和信息系统工作理解仍需结合实例检验。

## 背景

企业提出信息化时，常先想到要建设某种系统、增加某项功能，或改造一段流程。更前面的疑问是：为什么需要这些改变，它们应当服务什么业务结果？讨论业务需求起点，是为了找到提出改变的业务依据，使后续研究和设计有明确的方向。这一问题同时适用于新建系统和既有系统迭代。

## 目标

**通过理解业务需求的起点，明确组织需要达成什么结果、哪些业务需要优先研究，以及应当带着什么问题进入场景与痛点分析。** 在此基础上，逐步判断值得实现的改变及信息系统应承担的作用。

## 阅读主线

**先明确业务目的，再理解业务怎样运作；据此选择研究切口，通过具体场景核实需要，最后讨论改变目标与系统作用。**

下文按这条线展开。每一步形成下一步的依据，调查中的新发现也可以反过来修正前面的认识。

1. **确认业务目的**：组织要为谁达成什么结果。
2. **理解业务运作**：这些结果依靠哪些活动、参与者、对象和条件产生。
3. **选择研究切口**：本轮优先了解哪部分业务，为什么。
4. **进入场景与需要分析**：实际怎样做，哪些需要未满足，依据是什么。
5. **明确改变目标和系统作用**：希望改变什么，信息系统能够承担哪些工作。

## 1 确认业务目的

流程和对象能提供调查入口，但仅知道“有哪些步骤”“管理哪些东西”，还不能解释这些工作为什么重要。

**但第一性原理还应再上一层——组织要为谁达成什么结果，为此需要怎样的决策、协作与控制。**

首先需要理解企业服务谁、提供什么产品或服务、怎样创造价值和维持经营，以及承担哪些持续责任。不同参与者的诉求可能并不一致，需要明确结果的受益者、责任方与主要约束。

例如，一家设备运维企业需要在服务约定和资源条件下保障设备可用。“保障可用”提供持续的业务方向；“缩短故障响应时间”或“承接更多异地项目”则可能成为一次研究的动机，是否值得作为改变目标仍要结合实际情况判断。以下运维例子均为说明性假设。

**了解企业“是做什么的”，是为了理解它需要达成什么结果；了解业务流程，是为了理解这些结果怎样产生。**

这一步形成的是业务目的、相关参与者、期望结果和主要约束。它们使我们能够在下一步区分哪些活动与条件值得关注。对于局部改进，只需向上追溯到足以解释其价值和约束的层级。

## 2 理解业务怎样运作

知道需要什么结果之后，要解释组织依靠什么产生这些结果。业务流程与对象生命周期是其中两个视角：流程描述活动和协作的组织方式，生命周期描述业务对象随事件和活动发生的变化。它们还需要与**对象、角色、规则和外部依赖**等信息联系起来。

**理解业务，需要同时看工作如何开展、谁作决定和承担责任、依靠什么能力与资源，以及怎样获得信息并确认结果。** 下列视角用来避免遗漏与研究有关的条件，按具体业务取用，不是要求穷尽整个企业的固定分类表。

| 观察方面 | 需要了解什么 | 对后续研究有什么用 |
|---|---|---|
| 活动与协作 | 工作由什么触发，经过哪些活动，怎样交接和处理例外 | 定位需要深入观察的工作环节和协作关系 |
| 参与者与责任 | 谁执行、谁决定、谁受影响，谁接收结果并负责 | 找到调查对象，理解责任、权限与诉求差异 |
| 业务对象及其关系 | 围绕哪些人、物、事件或业务记录工作，它们如何关联、变化 | 识别状态、关系或业务记录上需要核实的问题 |
| 规则与决策 | 在什么条件下作什么判断，依据、权限和接受标准是什么 | 理解某一步为什么发生，判断哪些问题涉及规则或决策 |
| 能力与资源 | 需要什么专业能力，以及人员、时间、资金、设备和工具如何支撑工作 | 区分信息问题与技能、容量、资源配置等问题 |
| 信息与反馈 | 事实和知识从哪里来，何时可用、是否可信，结果如何反馈 | 定位信息缺失、延迟、不一致或结果不可确认的环节 |
| 外部关系与约束 | 怎样依赖客户、供应商和其他组织，受到什么经营条件或制度约束 | 看清组织边界外的影响，避免只研究内部流程 |

这些方面需要放在同一项业务里联系起来。例如，故障恢复流程涉及报修、派工、维修和确认；设备、工单、人员、备件是相关对象；诊断能力和备件储备影响能否修复；派工规则、接单责任和外部服务约定影响怎样协作；现场信息及运行数据影响判断是否可靠。

**业务流程与对象生命周期是理解同一业务的互补视角，角色、规则与责任把它们联系起来。** 一台设备的生命周期跨越采购、投运、维护和退役；一次故障处理又涉及多个对象。它们帮助我们识别哪些关系需要调查，不能单独决定痛点或系统功能。

这一步形成业务运作的初步认识，以及已知事实、异常线索和不确定之处。它给下一步选择研究范围提供依据。IIBA 的 BACCM 同样要求结合需要、价值、利益相关者与情境理解改变；上面的观察视角是为本问题作的综合整理，不是 BACCM 的原有分类。[IIBA BACCM](https://www.iiba.org/knowledgehub/the-business-analysis-standard/2-understanding-business-analysis/2-2-a-model-for-effective-analysis-baccm/)

### 输出物

**业务运作概览**，包含：

- **核心业务流程图或流程说明**：主要活动、开始与结束条件、关键交接。
- **核心业务对象及关系说明**：对象之间的联系；对有关键状态变化的对象，补充生命周期图或状态说明。
- **角色、规则与责任说明**：关联到上述活动和对象，说明谁执行、谁决定、依据什么，并按需标注信息、资源与外部依赖。
- **已知事实与待核实事项**：记录依据、异常线索和信息缺口，供下一步选择研究范围。

这些图表和说明可以合并维护，不要求各自独立成文。

## 3 选择本轮研究切口

有了业务目的和运作概貌，就可以判断从哪里深入。切口可以来自已有困难、一个新业务目标、外部条件变化，或希望建立的新能力，不要求先证明存在痛点。

**先建立业务全貌，再选重要场景深入；不必完整建模整个企业，才开始一次有价值的改进。** 选择时关注它对业务结果的影响、需要消除的不确定性，以及能否取得相关参与者和实际工作的证据。初始范围可以随着调查调整。

例如，从“保障设备可用”及相关工作概貌出发，可以先选取“故障发生到服务恢复”这段业务，研究各环节如何协作、哪些条件影响恢复时间。此时尚不能断定一定是派工慢，更不能直接决定建设工单系统。

### 输出物

**本轮研究范围与问题清单**，包含以下四项，供下一步开展场景与需要分析：

| 形成的内容 | 对调查的作用 |
|---|---|
| 业务目的与主要约束 | 说明为什么研究，以及什么结果值得关注 |
| 初始研究对象与范围 | 说明涉及哪些角色、环节和外部责任方，范围从哪里开始到哪里结束 |
| 候选业务场景 | 说明准备观察哪些具体工作、事件或实例 |
| 待核实问题与证据线索 | 说明已知什么、还不知道什么，以及可以向谁或从哪里核实 |

**业务目的提供判断相关性的依据，候选场景提供调查入口，研究问题把两者连接到具体取证。**

从业务目的到上述研究定向的工作，可以暂称为“业务理解与研究定向”。这是工作名称，不是独立于调查的一次性审批关口。GOV.UK 的发现阶段方法也强调先明确研究目标、问题与范围，并在研究中了解用户情境、约束及机会。[GOV.UK Discovery](https://www.gov.uk/service-manual/agile-delivery/how-the-discovery-phase-works)

## 4 通过具体场景核实业务需要

带着前一步的范围与问题，选择实际工作实例，访谈参与者并核对记录或观察实际操作。在同一场景中说明触发、活动、责任交接、对象变化和完成结果。

**在某种条件下，哪些角色围绕哪些业务对象，依据什么规则完成哪些活动，使业务达到什么结果，又通过什么事实确认这个结果。** 这句话用于检查关系，不要求所有工作都写成固定流程图。

在故障恢复的例子中，可以核对报告、派工、到场、维修、确认各环节。如果实例显示“派工前反复补问设备位置，造成到场延迟”，就得到一个候选痛点，再核实它的频率、影响范围和原因。若主要限制是备件等待或维修能力，则需要沿相应方面继续研究。

**工单结束，不自动等于设备已经恢复服务。** 因此还需确认完成标准由谁判断，依据是什么，记录状态是否真实对应业务结果。

**业务需要可以先存在，但尚未被人清楚认识或表达；问题与机会研究帮助我们发现和澄清这些需要。** 当事人提出的需求是理解需要的线索，也可能不完整或已经夹带某个解决方案。调查中要区分实际发生的事实、制度要求、分析判断与未来设想。

这一步形成带依据的业务场景、需要或痛点、影响、约束及关键未知。场景可以暂未发现痛点；新业务尚无实际运行时，则需要明确现有依据与待验证假设。所得结果既支持下一步的目标选择，也可以促使前面的研究范围调整。

## 5 明确改变目标与信息系统的作用

根据调查，先判断本轮希望改善什么、建立什么能力，再比较可能的改变方式，例如调整职责或流程、补足人员和资源、采用现成工具，或建设与改造软件。业务研究并不自动导出信息系统项目。[IIBA BACCM](https://www.iiba.org/knowledgehub/the-business-analysis-standard/2-understanding-business-analysis/2-2-a-model-for-effective-analysis-baccm/)

**连接业务与信息系统的关键，是业务需要完成哪些信息工作。** 要进一步明确：谁在何时需要知道什么，如何记录和传递事实，如何依据规则作出判断，怎样协调行动、确认结果和处理偏差。

作为继续讨论的工作理解，可以先把业务信息系统理解为组织承担相关信息工作的安排，涉及人、规则、流程、数据和技术。其严格定义和边界仍需进一步论证。这一理解帮助我们检查已有信息工作由什么承载，以及拟议系统应参与哪一部分决策、协作和控制。

**软件从 0 到 1，未必意味着业务从 0 到 1。** 企业可能早已通过台账、表格、电话和人工协作完成这些工作；新系统需要承接或改善它们。已有系统的迭代同样需要重新核对业务目标，而不能把现有软件行为当作业务应该如此的证明。

**信息系统承担什么，应由业务所需的信息工作和方案比较来决定。** 选择过程中还需考虑投入、使用和维护条件，建立相应的结果评价方式。**系统上线不能替代业务效果验证。**

这里形成的是改变目标、方案选择及系统分工的依据，随后才进入相应的产品与系统设计。前面确定的研究范围，和这里逐步确定的产品范围，是不同的决定。

## 方法的使用边界

**业务理解与研究定向 ⇄ 具体场景调查与痛点或其他需要识别 → 目标与范围确定。** 这表达相互提供依据的关系，不要求工作只能按一次固定顺序推进。调查可以从痛点、对象、异常事件或已有流程进入，再补足目的和相关条件。

前期只需取得足以指导下一步调查的信息；后续则需要与选择或投入相称的证据。相关未知应当明确保留，研究可以继续、调整范围或停止。新建与迭代都适用这一思路，但各自需要核实的业务假设、现状事实和改变影响会不同。
