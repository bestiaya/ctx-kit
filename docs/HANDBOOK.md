# 操作手册

先按 [Claude](../claude/README.md) 或 [Codex](../codex/README.md) 的说明安装。用户说目标、问进展、作必要决定；工具负责记录。

## 开工

说“开始推进这个复杂任务”，或调用 `ctx-kickoff` 并描述目标。先确定目标项目，复用相关案或新建案，给聊天一个易识别的名字，把案放进任务板。指标未确定就列未决，不替用户承诺数字。

默认在当前聊天继续。已要求派给某聊天或建立协调流程时按授权执行，不必每次问“在这儿聊还是派出去”。

两端会话共用 `C<案号>-<任期>｜<案短名>-<本任期工作>`，如 `C07-01｜计费-方案讨论`。新案任期从 01 起，接手读案头递增；派生执行用 `C07-01.1｜计费-压测-exec`。散活用 `C00-<板上登记行号>`，取号无需会话列表。用户指定名和运行中的旧名保留，同一任期重复调用不加号，详细规则见 [共用方法](METHOD.md#会话命名)。仅改名不为凑编号建案；没有既有案/散活/已派关系时先说明缺口。

## 看进展、拍板、收件

说“看任务板”或调用 `ctx-status`。默认汇报活跃案、在跑/待验收任务、待拍板和未处理来件；已结案案退出这些统计。收尾中、已结案但仍有在跑执行或未处置事项的案单独显示，不能被历史过滤隐藏。说“包括历史案”或点名旧案时，再展示结案类型、时间、原因和关联案。运行状态来自平台查询，项目状态来自案；不一致时明确指出。

说“采用方案 B，理由是……”后，持笔更新 C 与 B。来件先记 I，再执行并写结果；收到却没办完不能标完成。

## 派活与回收

每项独立任务有稳定 ID、自足任务书、输入/输出范围和验收条件。执行会话写自己的交付件，回报任务 ID 和路径；持笔验收后更新 E，说明对方案的影响。未测就标未测，部分完成就列剩余部分。

工具不可用时提供可复制的接手提示与文件位置，不把“任务书已写好”说成“执行会话已开始”。

## 换会话

说“交接这个案”或调用 `ctx-handoff`。先标收口中，保存并核验成果与缺口，再释放持笔；随后必须给交出的旧会话原标题加一次 `✕ `，给接手提示。已有前缀不叠加，未完成交接不提前标记；改名不可用或失败时明确报告 UI 标记未完成，与已完成的文件交接分别说明。标记只作识别，不删除、归档或关闭聊天，也不改继任持笔。详见[共用退役标记规则](METHOD.md#交接后的会话退役标记)。

新聊天说“接手案文件 `<绝对路径>`”，或调用 `ctx-takeover`。读取状态、H 缺口、I 收件和未合并来件，核对关键文件后认领持笔，简短复述目标、进展和下一步。用户要求继续且无关键阻塞时直接继续；要求抽查或缺少必要决定才等待。

无法恢复的内容留在 H，不能为了显示交接完成而删掉。旧案格式可直接读取，不需要先转换成新模板。

## 案不用了、做完了或被替代

直接说“C-07 不用了”“终止 C-07”“C-03 和 C-05 已被 C-14 替代，结束它们”，现有 `ctx-handoff` 会执行共用结案流程，不需要新增命令。类型分别记为完成、终止或合并，保留案号、历史和文件原路径，安置未完成任务与来件后释放持笔。有任务仍在跑或转交尚未获接收时，先显示结案中及待收尾事项。

终止不表示目标完成，也不表示全部历史结论失效。结案不会自动归档聊天或停止进程。说“哪些旧案可以结束”只会列出候选；直接指定终止对象则执行，不再逐案重复询问同一授权。

以后说“重新做 C-07”即可恢复原案，按正式认领递增任期，保留前次结案记录。仅查看旧案不会重开，也不会自动重新启动旧任务。操作细节见 [共用流程](../workflows/case-lifecycle.md)。

## 入口习惯

用自然语言表达要做的事即可：开工、看进展、交接、终止、恢复、方案送审和协作检查都由现有技能分流，原来的显式调用仍可用。功能内部有多个动作时，不要求用户记住子命令；只有意图确实不明时才问必要问题。

例如画像能力若已安装，“更新我的画像”“把画像接入当前 agent”应由该能力分别映射到更新、适配。该能力未安装时如实说明，不把这里的使用原则当作功能已经存在。

## 方案送审

说 `ctx-review to claude` 或“把这个方案交给 Claude 审核”。原持笔准备简短问题和必要原文，默认通过 CLI 发起并回收。审核方讨论整体判断、实质异议与替代方案，不默认逐链接核验；版本和执行检查由调用方承担。用户确认结论和拟改范围后才改文件。

同一目标最多三轮内容往返，有充分结论就提前收口；有进展继续等待，长期无进展排查报告，不默认到点终止。用户也可明确选择人工转读，完成后说“审核好了”；回执版本与进展仍归原案 E/I。详见 [共用送审流程](../workflows/review.md)。

## 方法说明文档写作

说“使用方法说明文档写作，为某类读者说明怎样开展这项工作”，或调用 `ctx-method-doc`。可带主题、读者、已有材料和篇幅要求；已有上下文足够就不重复索取。按流程推进、判断取舍或概念关系选择主线，骨架可以裁剪；范例的业务步骤不是通用模板。

核心判断及用户明确保留的原句加粗，成熟方法保留官方来源与支持范围。对文档提出异议时先回应，取得明确同意后再写入；直接要求创建或修改则按授权执行。普通 README、案卷、短邮件和纯数据报告沿用原文类，详见 [共用写作流程](../workflows/method-doc.md)。

## 协作与上下文审核

`ctx-checkup` 先只读检查持笔冲突、失效指针、来件遗漏、交付验收和结论依据。默认不自动改名、抢持笔、归档或修复历史。

复杂任务完成或形成阶段样本后，用 [审核记录](../templates/AUDIT.md) 分别回答缓存/交接整体成本，以及不同上下文占用下的质量。数据不足写“判不出”；调用审核不自动创建定时任务。
